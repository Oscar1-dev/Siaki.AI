# Phase 12 — Policy engine

## Delivered

- Rust-owned, SQLite-backed policy engine (`policy.sqlite3`, WAL, `user_version` migrations) — the deterministic authority boundary between model proposals and side effects.
- **Deny-by-default evaluation**: `evaluate(actor, capability, resource, arguments)` returns `allow` / `deny` / `approval_required`. Only `allow` authorizes execution. Internal-tier capabilities (reason/plan/notes) auto-allow; everything external needs an owner grant or an approved request.
- **Risk tiers**: capabilities map to `internal` / `low` / `external` / `financial` / `critical`; unknown capabilities fall to `critical` (most restrictive).
- **Typed capability grants**: bound to capability, resource pattern (exact or trailing-`*` prefix), purpose, action count, optional spend ceiling, and expiry. Grants are consumed per use (action + spend accounting) and are immediately revocable.
- **Approval queue with exact-payload binding**: an approval stores a SHA-256 digest of the canonical arguments; a materially changed payload no longer matches, so a prior approval cannot be reused for a different action.
- **Emergency kill switch**: when engaged, every evaluation returns `deny` regardless of grants or approvals.
- **Append-only audit log**: every evaluation and owner action is recorded; there is no command that edits or deletes audit rows, so the UI cannot rewrite history.
- Owner "Policy" workspace tab: evaluate a model-proposed action, create/revoke grants, resolve approvals, toggle the kill switch, and read the audit log.
- Typed IPC contracts, runtime guards, and command-name stability for all eight commands.

## Completion gate

The gate is "forbidden tool calls fail even when generated by the model."

This is enforced structurally and verified by tests:
- A model-proposed external capability (`email.send`) with no grant evaluates to `approval_required`, never `allow` — so it is not executed.
- An owner grant then authorizes it (`allow`); revoking the grant returns it to `approval_required`.
- The action-count and spend limits turn an over-quota call into `deny`.
- The kill switch forces `deny` even with an active grant.
- An approval authorizes only the exact payload digest; a changed `amount` is not covered.
- Unknown capabilities are `critical` and require approval.
- Grants and the kill switch persist across restart; evaluations are audited.

The model's only entry point is `evaluate_action`; every authority-granting command (create/revoke grant, approve, kill switch) is an owner command with no model-reachable path, so model output can never grant, widen, or approve authority.

## Boundaries (not in this phase)

- **No executor yet.** This engine decides; it does not itself perform actions. The tool executor that calls `evaluate` and acts only on `allow` (with idempotency and rollback) is a later phase. The Phase 05 workspace approval inbox remains an explicit placeholder; this Policy tab is where the real engine is exercised.
- Approval requests are created explicitly here; autonomous generation by the supervisor is Phase 18.
- The audit log is append-only at the application layer (no edit/delete commands); database-file tamper-resistance (signing/WORM) is a later hardening concern.

## Limitations

- Unencrypted local SQLite.
- Spend accounting reads an `amount` field from the arguments; richer financial modelling (currencies, holds) is deferred.
- Capability→tier mapping is a fixed table; owner-editable tiering is a later concern.
